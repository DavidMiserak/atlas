## Problem Statement

You follow a structured 4-day bodybuilding program (from your training doc) with specific structure: warm-up progressions, working sets at %1RM or RPE targets, exercise variants, and progression rules. Right now you either:

- Log workouts manually in a notebook (tedious)
- Use a generic fitness app (doesn't enforce your program structure, doesn't handle variant swaps mid-session)

You need a tool that:

1. **Enforces structure** — guides you through warm-ups → working sets → accessories in order, preventing skips or mistakes
2. **Handles machine unavailability** — lets you swap exercise variants mid-session (barbell → dumbbell → machine) without losing progress tracking
3. **Tracks 1RM and PRs** — maintains 1RM history, auto-recalculates working set weights when 1RM updates, shows your strength progression over months/years

## What Makes This Cool

**Your training program becomes your app.** No manual data entry. The app understands your program's structure (warm-up sets, working sets, rep ranges, %1RM targets) and guides you through each session like a coach at the gym.

**Machine swap without friction.** Mid-session? Machine taken? Switch to a different variant (dumbbell instead of barbell) and the app recalculates warm-up progression and working set weights instantly. No re-logging, no data loss.

**1RM is the hub.** Update your 1RM once after hitting a PR. Every future session auto-recalculates its working set weights. The app tracks your 1RM history — see your strength arc over a year.

**Local and offline.** Everything on your phone. No cloud, no account, no network dependency. Your training data is yours.

## Constraints

- **Local-only**: All data stored on device. No cloud sync, no server.
- **Offline-first**: Zero network dependency. Works in a basement gym.
- **Phone-first UX**: One-hand usable at the gym. Large buttons, quick taps, minimal typing.
- **Program-agnostic data model**: Should work for other training programs (not just your 4-day split), in case you switch systems later.

## Premises

1. **The app is the "structured guide" at the gym** — it walks you through warm-ups → working sets → accessories in order. Structure prevents mistakes.
2. **1RM is the single source of truth** — update it once, all future sessions recalculate. The app maintains a 1RM history so you see your strength arc over time.
3. **Exercise variants are flexibly swappable mid-session** — Each slot (Horizontal Push, Squat Variant, Hip Hinge Variant) has multiple variants. You can pick at the start, but **swap anytime** if a machine becomes unavailable. The app recalculates warm-up weights and working set targets based on your chosen variant for that session.
4. **This is for you first** — we're not designing for "everyone"; we're designing for your specific workflow and the training system you follow.

## Approaches Considered

### Approach A: Normalized SQLite Schema ✓ CHOSEN

Structured relational database. Programs, exercise categories, variants, 1RMs, session history all normalized.

### Approach B: JSON Programs + Transactional Session Logs

Programs as JSON data, sessions logged as plain JSON objects. Simplest, but harder to query history.

### Approach C: Document Store (Hive)

NoSQL-style boxes. Flexible, queryable, Flutter-native. Middle ground between SQL rigor and JSON simplicity.

**Chosen A because:** You care about structure and consistency. The data model is the foundation — once locked in, everything else is straightforward. You get queryable 1RM history, deload logic becomes debuggable, and you can instrument later ("why did I stall on squats?").

## Recommended Approach: SQLite Schema

### Core Data Model

The schema enforces the training program structure: programs contain workout templates, workout templates contain exercises (slots), exercises map to variants, sessions log actual performance.

```
PROGRAMS
├─ program_id (PK)
├─ name (e.g., "4-Day Novice Bodybuilding")
├─ version (e.g., "v1", "v2") — incremented on major updates
├─ description
├─ created_at, updated_at

WORKOUTS (templates, e.g., "Day 1 - Lower Strength")
├─ workout_id (PK)
├─ program_id (FK)
├─ name (e.g., "Lower Body Strength")
├─ day_number (1, 2, 3, 4)
├─ order_in_program
├─ notes (e.g., "Strength focus")

EXERCISE_SLOTS (the category, e.g., "Squat Variant")
├─ slot_id (PK)
├─ workout_id (FK)
├─ name (e.g., "Squat Variant")
├─ slot_order (1st, 2nd, 3rd exercise in workout)
├─ category (e.g., "Compound Lower")

EXERCISE_VARIANTS (the specific exercises, e.g., "Back Squat", "Front Squat")
├─ variant_id (PK)
├─ slot_id (FK)
├─ name (e.g., "Back Squat")
├─ description (notes about form, ROM, etc.)

SET_TEMPLATES (the prescribed sets for a slot)
├─ set_template_id (PK)
├─ slot_id (FK)
├─ set_number (1st warm-up, 2nd warm-up, 1st working, 2nd working, etc.)
├─ set_type (e.g., "warm-up", "working", "back-off")
├─ reps_target_min, reps_target_max (e.g., 5, 5 or 8, 10)
├─ percentage_1rm (e.g., 50%, 70%, 82.5% — NULL if RPE-based)
├─ rpe_target (e.g., RPE 8 — NULL if %1RM-based)
├─ rest_seconds (e.g., 180)

VARIANT_ONE_RM_HISTORY (1RM tracking per variant, not per lift)
├─ history_id (PK)
├─ variant_id (FK) — the specific variant (Back Squat, Front Squat, etc.)
├─ weight (lbs)
├─ date (when it was established/updated)
├─ notes (e.g., "Hit triple at this weight")
├─ is_current (true/false — current 1RM for this variant)

SESSIONS (actual workouts logged)
├─ session_id (PK)
├─ workout_id (FK)
├─ date_completed
├─ is_deload (boolean) — true if this session is a deload week (lower intensity)
├─ notes

SESSION_EXERCISES (the slot + variant chosen for THIS session)
├─ session_exercise_id (PK)
├─ session_id (FK)
├─ slot_id (FK)
├─ chosen_variant_id (FK) — the variant picked (or swapped to mid-session)

SESSION_SETS (actual performance)
├─ session_set_id (PK)
├─ session_exercise_id (FK)
├─ set_number
├─ reps_completed
├─ weight_lifted (lbs)
├─ one_rm_at_session_time (lbs) — the 1RM value used to calculate this set's target (historical snapshot)
├─ rpe_actual (what you actually felt, 1-10)
├─ notes (form breakdown? felt strong?)
├─ timestamp (for rest period tracking)
```

### Workflow at the Gym

1. **Session Start**: Open app, select "Day 1 - Lower Body Strength"
2. **First Exercise**: App shows "Squat Variant — warm-up set 1: 8 reps @ 50% 1RM". Shows suggested weight (e.g., 155 lbs if your squat 1RM is 310). Shows rest timer.
3. **Variant Swap** (mid-session): Machine taken? Tap "Choose a different variant" → select "Front Squat". App recalculates warm-up progression and working set targets for front squat (if it has a different 1RM).
4. **Log Sets**: For each set, tap reps completed, weight, RPE. App stores it.
5. **1RM Update**: After the session, tap "Hit a PR on Squat" → enter new 1RM → app updates history, recalculates future session targets.

### Key Design Decisions

**Variant-Specific 1RM Tracking (DECISION B)**: Each exercise variant has its own 1RM history. Back Squat and Front Squat track separate 1RMs because they have different strength profiles. When you swap variants mid-session, the app uses that variant's 1RM for weight calculations.

**Variant-Swap Handling**: When you swap a variant mid-session, the `session_exercises.chosen_variant_id` points to the new variant. All calculations (warm-up, working sets) use the new variant's 1RM. The session record shows the swap: "Back Squat: 2 sets logged, then switched to Front Squat: 3 sets logged."

**Warm-Up Progression Algorithm** (from `docs/ms-training-bb.md`): For each main lift:

- Warm-up Set 1: 8 reps @ 50% of first working set weight
- Warm-up Set 2: 4 reps @ 70% of first working set weight
- Warm-up Set 3: 2 reps @ 90% of first working set weight

_Example: Squat working set is 260 lbs. Warm-ups are: 130 lbs × 8, 182 lbs × 4, 234 lbs × 2._

**Weight Rounding**: All calculated weights (warm-ups, %1RM targets) round to the nearest 5 lbs. (259.875 → 260 lbs). User can override in-session if needed.

**Historical 1RM Snapshots**: Each `SESSION_SET` stores the 1RM value used to calculate its target weight. When you update 1RM mid-year, past sessions show what you _actually_ lifted at that time, not recalculated targets. This keeps your history accurate.

**Deload Flag**: Sessions can be marked as deload weeks (e.g., 60-70% intensity instead of normal 82.5%). Flag added to SESSIONS table: `is_deload BOOLEAN`. The app alerts you when it's time to deload (every N weeks, configurable).

**1RM Auto-Recalculation**: When you update 1RM (hit a PR), all _future_ sessions auto-recalculate their targets using the new 1RM. Past sessions retain their historical 1RM snapshot and show what you actually did.

**RPE vs %1RM Coexistence**: The schema supports both. `set_templates.percentage_1rm` is NULL for RPE-only sets. `set_templates.rpe_target` is NULL for %1RM-only sets. At session log time, you enter actual RPE and weight — the app stores both.

**Program Seeding**: Programs load from JSON (your training doc → JSON) on first app launch. After seeding, programs live in SQLite. Program updates require a new version (immutable program records).

## Decisions Locked In

✅ **Variant-specific 1RMs** — Each variant (Back Squat, Front Squat) tracks its own 1RM history.
✅ **Weight rounding** — All calculated weights round to nearest 5 lbs.
✅ **Historical accuracy** — SESSION_SETS store the 1RM used at session time, showing what you actually lifted.
✅ **Deload flag** — SESSIONS marked with `is_deload` boolean for deload weeks.
✅ **Warm-up algorithm** — 50% → 70% → 90% of first working set weight (from training doc).

## Additional Decisions (Edge Cases)

✅ **Variant swap with missing 1RM** — If you swap to a variant with no 1RM history, the app prompts: "Estimate {Variant} 1RM for this session?" You enter a temporary value. After the session, update the 1RM properly.

✅ **Incomplete sessions** — If the template calls for 3 sets but you complete 2, the app logs those 2 and prompts: "Template calls for 3. Log the last one?" You can skip it (with a warning), or stop early. The session records exactly what you did.

✅ **Program versioning** — Programs are immutable. When you update your program (6 months later), create a new PROGRAM record (v2). Old sessions point to the original version. New sessions use v2. Add `version` column to PROGRAMS table.

## Open Questions (Deferred to Phase 2)

1. **Deload frequency**: Hardcode to every 4 weeks for MVP. User-configurable later.
2. **Form coaching**: In-app form videos, cues, technique tracking. Defer to Phase 2.
3. **Multi-user**: MVP is single-user, device-only. Defer multi-user sync to Phase 2.
